# AskAlbum M1 双模型并行启动说明

版本：draft 0.1  
当前范围：跳过 M0，直接完成本地 VLM 与 API VLM 的结构化标注

## 1. 这阶段只做什么

两个人对同一批图片使用：

- 同一张处理后的图片；
- 同一份 [`prompt_v1.md`](./prompt_v1.md)；
- 同一份 [`annotation_payload.schema.json`](./annotation_payload.schema.json)；
- 同一份每张图结果格式 [`candidate_record.schema.json`](./candidate_record.schema.json)。

然后分别得到：

```text
candidates_local.jsonl
candidates_api.jsonl
```

这一阶段不做 M0，不给模型任何预分类，不根据图片类别修改 Prompt。

## 2. 两个人如何并行

### 共同准备一次

- [ ] 从 train 中选择相同的 12 张 smoke 图片；
- [ ] 统一图片方向、颜色格式和尺寸；
- [ ] 为每张处理图计算 SHA-256；
- [ ] 确认 Prompt 版本和两个 JSON Schema 不再临时修改；
- [ ] 建一份双方共同读取的图片清单。

图片清单每行至少包含：

```json
{
  "image_id": "1400",
  "split": "train",
  "processed_path": "artifacts/images/img-v1/1400.jpg",
  "processed_sha256": "..."
}
```

12 张 smoke 应覆盖普通照片、多人、文字、室内、食物、自然、弱光、展品、插画、文档/屏幕、低分辨率和极端宽高比。validation 不进入 smoke。

### L：本地开源模型负责人

- [ ] 冻结精确 checkpoint 和推理依赖版本；
- [ ] 读取共同图片清单；
- [ ] 使用共享 Prompt 和 Schema 调用本地模型；
- [ ] 保存模型原始返回；
- [ ] 校验并输出 `candidates_local.jsonl`；
- [ ] 记录显存、速度和失败原因。

### A：API 模型负责人

- [ ] 冻结 provider 和精确 model ID；
- [ ] 用 1 张图确认图片上传、结构化 JSON、usage 和错误格式；
- [ ] 读取共同图片清单；
- [ ] 使用共享 Prompt 和 Schema 调用 API；
- [ ] 保存原始返回，并实现超时、429/5xx 重试和缓存；
- [ ] 校验并输出 `candidates_api.jsonl`；
- [ ] 记录用量、费用、速度和失败原因。

双方不能看到对方的模型答案后再修改自己的 Prompt。

## 3. 单张图片的处理步骤

```text
读取图片清单的一行
       ↓
读取 processed_path 并核对 SHA-256
       ↓
发送图片 + prompt_v1.md
       ↓
要求模型按 annotation_payload.schema.json 返回 JSON
       ↓
保存原始响应
       ↓
解析 JSON，并做 Schema 与语义检查
       ↓
外面补上 image_id、模型名和状态
       ↓
追加到 candidates_local/api.jsonl
```

## 4. 模型直接输出与落盘记录的区别

模型直接输出的是 `annotation`，格式由 `annotation_payload.schema.json` 规定：

```json
{
  "scene": {},
  "capture_visual": {},
  "entities": [],
  "ocr": [],
  "relations": [],
  "event": {},
  "subjective": {},
  "captions": {},
  "uncertainties": []
}
```

程序落盘时在外面加一层：

```json
{
  "image_id": "1400",
  "processed_sha256": "...",
  "source_kind": "local",
  "model_id": "实际模型ID",
  "prompt_version": "m1-shared-v1.0.0-draft",
  "annotation_schema_version": "1.2.0",
  "status": "succeeded",
  "raw_response_path": "raw/local/1400.json",
  "annotation": {},
  "error": null
}
```

这层记录的目的只是让两边结果能按 `image_id + processed_sha256` 对齐，并能查到原始响应和模型版本。

## 5. 语义检查

JSON Schema 检查字段和类型，程序还要检查：

- `entity_id` 是否为连续的 `e1/e2/...`；
- relation 和 event 引用的 entity ID 是否存在；
- bbox 是否满足 `x1<x2, y1<y2`；
- `count=null` 时 `count_exact=false`；
- 非 person 的 `attire_zh` 是否为空；
- `secondary_types` 是否包含 primary；
- OCR 为空是合法结果，不自动算失败。

事实内容不能由程序自动猜着修。模型输出无效时保留原响应，并将该图记录为失败或重试。

## 6. 第一轮如何比较两份答案

第一轮 12 张不要急着写复杂自动评分，先把字段并排展示并人工核对，确认两边粒度一致。

| 字段 | 比较方式 |
|---|---|
| scene/capture | enum 是否一致；unknown 与明确值单独标出 |
| entities | 名称同义词、位置和框大致重叠，找出描述同一对象的两项 |
| count | 对齐到同一实体后比较整数；null 不与整数强行判一致 |
| attributes | 分别比较颜色、状态、动作和服饰，不比较整句文字 |
| OCR | 先统一空格和全半角，再比较字符差异和位置 |
| relations | 对齐实体后比较“谁、什么关系、对谁” |
| captions | 不逐字比较；检查是否只使用前面已有事实，以及是否新增幻觉 |
| subjective | 作为主观结果保留，不作为硬事实冲突 |

处理原则：

```text
两边都明确且一致 -> 接受
一边明确、一边 unknown/null -> 标记待确认
两边明确但冲突 -> 查看原图或裁剪区域复核
只有一边提到实体 -> 不直接接受，也不直接删除
```

等 12 张人工核对稳定后，再实现批量字段匹配代码。

## 8. 第一阶段完成条件

- [ ] 12 张图片在两边使用相同 `image_id` 和 `processed_sha256`；
- [ ] 两边 Prompt 文件 hash 相同；
- [ ] 两边 annotation Schema hash 相同；
- [ ] 每张图在两个 backend 都有 succeeded 或明确 failed 记录；
- [ ] 成功记录通过 Schema 和语义检查；
- [ ] API 没有重复计费调用，日志没有 API key；
- [ ] 两个人完成一次逐字段人工核对；
- [ ] 发现的问题归类为 Prompt、模型能力、图片质量或程序错误；
- [ ] 12 图通过后才扩大到 `prompt_dev_50`。
